# 候选方案编排

[首页](../../README_zh.md) · [工作台](workbench.md) · [English](../en/orchestration.md)

可选 Workbench 通过现有 Harness 协调候选编写与执行。主 Agent 整理上下文、委派提案、
审阅候选文件，再提交获准执行的任务。每个 Campaign 的 `EvolutionController` 继续负责
状态、预算、评价契约、调度与恢复。独立 CLI 与 DSH 插件沿用原有接口。

## 提案、审阅与执行

主会话可调用 `dataevolver_delegate`，显式提供任务上下文：

```json
{
  "name": "另一种数据配方",
  "task": "阅读选定的执行记录，编写候选配方，说明假设、预期效果及待检查项。不要执行候选。",
  "mode": "proposal",
  "contextJobIds": ["previous-job-id"]
}
```

将示例 ID 替换为工作台保留的任务 ID，也可传空列表。子会话采用配置的子 Agent
Provider 与模型。提案会话在私有会话目录内取得独立、初始为空的本地工作区和产物目录。
父工作区作为来源引用，工作台不会复制或软链接整份源码。

使用 `dataevolver_child` 查看、等待或停止子会话。子会话不能再次委派。
主 Agent 审阅候选文件后，再准备计划或 Worker Profile。执行仍经过 `compile-plan`
或 `worker-compile`、`create` 和有界 `step`。`resume` 会立即执行任务。
工作台不会自动采纳文件、晋升知识或修改冻结的评价器与预算。

提案会话通过 Workbench 桥接接口只能调用 Harness 的 `status`、`explain` 和 `replay`。
桥接接口会拒绝图像调用与修改状态的 Harness 命令。原生 Agent 工具仍具有宿主机账号权限。
**工作区分离不等于操作系统隔离或安全沙箱。** SSH 配置仍指向原来配置的远端源码目录；
本地提案目录不会自动创建或同步远端工作区。

省略 `mode` 或设置为 `task`，会保留普通委派的共享工作区和原有工具访问方式。
此模式用于已获授权的任务，不提供候选文件隔离。

本地提案通过桥接查询 Campaign 时，相对路径以源工作区为基准。
候选文件写入提案工作区。SSH 查询以配置的远端工作区为基准。

## 执行上下文

`contextJobIds` 最多选择 16 个不同任务。后端将传输状态、退出码、来源路径及有界日志
末尾内容写入私有 `context.json`。日志按字节范围读取，不会为了收集上下文加载整份
引擎日志。上下文会脱敏，并受 `maxContextBytes` 限制。
会话记录保存文件路径及文件字节的 SHA-256；
后端在启动或重新打开 Agent 进程前核对摘要。

快照记录执行观察，包括失败与效果不明的任务。后端不会从任意日志文本推断质量分数
或验收成功。记录和日志片段可能来自尚未结束的任务，采纳候选前仍应核对当前回执。
修改活动会话的上下文文件，不会更新 Agent 已经读入的内容。

主 Agent 可根据这些观察整理不同假设。可复用知识继续经过 `CapabilityStore`，
并通过现有 `PROMOTED` 经验的任务、模型、版本和约束兼容性检查。
执行成功不能单独证明视觉质量、下游训练收益、方法改进或泛化。

## 限额与队列

在私有配置的 `orchestration` 或 **设置 → Agent 运行时 → 候选方案编排** 中修改限额。
旧版 version-1 配置加载时会补充本节默认值，其他未知字段仍会被拒绝。

| 配置字段 | 默认值 | 含义 |
|---|---:|---|
| `maxOpenChildren` | 4 | 子 Agent 进程上限，包含空闲子会话；完成后停止子会话可释放名额。范围：1–32。 |
| `maxConcurrentJobs` | 1 | Workbench 执行任务并发上限。范围：1–32。 |
| `maxQueuedJobs` | 16 | 等待执行的请求上限，包含记录尚未写完的请求。范围：1–256。 |
| `maxContextBytes` | 32768 | 上下文序列化后的 UTF-8 字节上限。范围：1024–1048576。 |

会修改状态的 Harness 命令进入有界先进先出队列。`status`、`explain`、`replay` 和
`pause` 可绕过队列，便于查询与提交暂停请求。暂停何时生效仍由 Controller 决定。
队列满时返回错误，不启动进程。

排队请求保留参数与部署配置快照。所引用的计划和 Profile 文件仍遵循原有编译及冻结规则。
当前 Workbench 限额约束新请求与派发；降低限额不会终止已有进程，提高限额可能派发
已排队任务。这些是每个 Workbench 进程内的限额，不是整台主机的 GPU 配额、模型 API
速率限制，也不会约束直接 CLI 或 Agent 原生命令。

## 取消与恢复

- `POST /api/jobs/{id}/cancel` 可取消未派发任务，Harness 回执面板提供相同按钮。
  此操作不会停止运行中的 Worker。
- Agent abort 或 stop 会取消该会话的排队任务。主会话 abort 仍会停止子会话。
  原生效果需要另行核对。
- 关闭工作台会取消待执行项。服务重启后，查询会将保留的排队任务显示为 `cancelled`，
  将失去进程关联的运行中任务显示为 `unknown`。两者都不会自动重放。
- 执行或暂停任务效果不明时，工作台会在继续自动派发前取消等待执行任务。后续任务需要显式提交；
  提交前应先检查 Campaign 与原生回执。
- SSH 传输结束不代表远端进程已经停止。

## 理论依据与限制

[Hyra 官方说明](https://hy.tencent.com/research/hyra)描述了上下文整理、多候选提案、
独立执行沙箱与资源限制。[AI4AI 目录](https://github.com/Tencent-Hunyuan/Hyra-results/tree/8443f9a9aae1a0b72c79e0b2908c79026b8e1555/AI4AI)
公开的是最终方案，未提供完整编排实现。本改动借鉴这些设计，并使用 DataEvolver
已有接口；没有引入 Hyra 运行时、指定模型或第二套 Controller。

预期作用是减少候选文件冲突、限制派发数量，并保留可追踪的反馈。
这些机制不能证明候选质量或训练收益提高。评价器共同演化与 Benchmark 探针不在本轮范围内。
本轮仅做静态审查；附带的契约测试未运行，运行行为与性能仍待验证。
